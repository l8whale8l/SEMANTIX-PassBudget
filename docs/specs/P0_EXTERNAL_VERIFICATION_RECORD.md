# P0 external verification record

- Review date: 2026-09-03
- Scope: orbit-to-ground contact-window calculation only
- PM verdict: **GMAT cross-tool verification PASS; P0 product release still BLOCKED on integration**
- Required CI status: **PENDING**

## 1. What was verified

The verification answers one bounded question:

> Given the same orbit, ground-station coordinates, elevation mask, time window and numerical
> conventions, does the product implementation calculate the same AOS, LOS, pass duration and
> maximum elevation as an independently implemented orbit tool?

It does not certify KMU-ET02 performance, radio-link throughput, RF reception quality or real-world
pointing accuracy.

## 2. Implementations and versions

| Role | Implementation | Version | Distribution role |
|---|---|---|---|
| Product calculation | `python-sgp4` plus `semantix_passbudget.adapters.orbit` | `sgp4 2.27`, Python 3.12.13 | Product-side implementation |
| Independent oracle | NASA GMAT `SPICESGP4` and `ContactLocator` | GMAT R2026a | Offline evidence generation only |
| Database verification | PostgreSQL | 17.6 | Disposable local test cluster |

GMAT is not included in the product and is not needed at runtime. Orekit was not executed in this
verification. For the lean P0 scope, GMAT is the required independent oracle and Orekit is an
optional future confidence check, not a release blocker. Architecture documents must state this
consistently.

## 3. Frozen inputs and method

Two evidence sets were compared:

- `EVD-ORB-01`: SGP4/TLE propagation with synthetic ground-station coordinates.
- `EVD-ORB-02`: a synthetic 700 km circular, 98-degree inclination, `TWO_BODY_V1` orbit with
  synthetic ground-station coordinates.

Both sides used the same documented time, frame, Earth-model, elevation-mask and clipping rules.
The product output was compared with static expected tables parsed from preserved GMAT reports.
Expected values were not generated by the product implementation. The executable comparison is
`tests/integration/test_orbit_cross_tool.py`; the complete numerical contract is
`docs/specs/ORBIT_VERIFICATION_CONTRACT.md`.

Coverage includes ordinary multi-pass windows, analysis-window start/end clipping, zero-contact
stations, low-elevation passes and a tangent pass close to the 5-degree elevation mask.

## 5. Defect found by the independent comparison

The first `EVD-ORB-02` comparison failed with an AOS difference of up to 22.3 seconds and an
Earth-fixed position difference of 18.29 km. The inertial states agreed, isolating the problem to
the frame transformation. The IAU-76 precession middle rotation `R2(theta)` had been implemented
about the X axis instead of the Y axis. Correcting the axis reduced the Earth-fixed discrepancy to
within 0.1 m and brought the fixture inside every ceiling.

This is the strongest evidence that the cross-tool gate was useful: the faulty output was
plausible and would not have been caught by product self-comparison.

## 7. Explicit limitations

- Every station coordinate in the evidence is synthetic and is not a verified KMU ground station.
- `EVD-ORB-01` uses a non-KMU object; `EVD-ORB-02` is entirely synthetic.
- UT1-UTC and polar motion are forced to zero for implementation comparability. The result proves
  agreement on a defined problem, not absolute real-world timing.
- Atmospheric refraction, horizon masks, light time and operational station availability are not
  modelled.
- No RF link budget, modem performance, packet loss or real reception data was validated.
- The raw CelesTrak-derived TLE must not be published until redistribution rights are resolved; a
  licence-clear or project-generated synthetic TLE is preferred for the public fixture.
- The verification was executed locally with an external calculation tool. It is cross-tool
  verification, not an independent audit performed by a separate V&V organisation.

## 8. PM release decision

The orbit **evidence gate is accepted** for the lean P0 scope. Additional Orekit work, H100 testing,
high-fidelity Earth orientation, Docker restart testing and PostgreSQL operations are not required
to proceed with the core product.

The product release remains blocked because `ScenarioSnapshot` still rejects `ORBIT_DERIVED` and
the verified orbit adapter is not connected to the user journey. The correct release status is:

`P0_RELEASE_BLOCKED_ORBIT_INTEGRATION`

The remaining P0 path is deliberately small:

1. Connect orbit/TLE and station inputs to `ORBIT_DERIVED` contact generation.
2. Feed generated contact duration into the existing assumed-throughput capacity calculation.
3. Feed that capacity into the existing model-output prioritisation flow.
4. Add one end-to-end golden scenario and preserve explicit assumption/provenance labels.
5. Run the required GitHub Actions workflow on Ubuntu and fix it until green.

Only after these steps may the project claim that a user can estimate daily contact time, daily
transfer capacity and which model outputs should be transmitted first.
